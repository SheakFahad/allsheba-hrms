User manual & technical overview — attendance, leave, payroll, expenses and reports
All Sheba Limited
Version: November 2026

1. What the software does

A web-based Human Resource Management System that runs in any browser (computer or phone). It keeps the employee register, daily attendance with late tracking, GPS-verified self check-in, leave, payroll, salary payments, daily expenses with printable vouchers, and produces every report as Print, PDF, Excel or CSV.

Addresshttps://allsheba-hrms.vercel.app (live / production)  ·  a separate staging copy with test data is used to try changes first
Who signs inEveryone signs in with a username + password (no e-mail needed). The role decides which panel opens.

Three roles

RoleOpensCan do
AdministratorAdmin panel /adminEverything: employees, attendance (any date), corrections, leave approval, payroll, salary payments, expenses (confirm payments), reports, users, settings, audit log. Never restricted by location.
Entry operator
(“user”)		Entry panel /entryQuick daily attendance for all employees, today’s overview, own entry history, correction requests, leave applications on behalf of staff, daily expenses only if the admin allows it. No salary, payroll, settings or personal data. No GPS needed.
EmployeeEmployee portal /meOwn GPS check-in / check-out, own attendance history, today’s Present list, apply for / cancel own leave, view own profile (read only). Cannot see anyone else’s data, salary or settings.

3. How the system fits together

Security is enforced in three places: the proxy (must be signed in), the server action (must have the right role), and the database itself (row-level security). Hiding a button is never the only protection.

How to make a change (for a developer)

  1. Open the folder in VS Code. Install once: npm install. Run locally: npm run dev → http://localhost:3000.
  2. A page’s look → its page.tsx in src/app/…. A menu item → src/components/layout/nav-config.ts. Saving logic → the matching *-actions.ts. A report → src/lib/reports/builders.ts and catalog.ts.
  3. A database change → add a new numbered file in supabase/migrations/ (never edit an old one). Use add column if not exists / create or replace function; never drop data.
  4. Check before sharing: npm run typecheck, npm run lint, npm test, npm run build. All must pass.
  5. Commit to branch staging and push. Apply the migration to the staging database (npm run db:migrate:staging) and test on the staging site.
  6. Only after the owner approves: back up production, migrate production, then merge staging → main (see section 9).
Never commit .env.local or .env.staging.local, and never paste keys or passwords into chat, screenshots or e-mail. If a key is exposed, create a new one in Supabase, update Vercel, then delete the old one.

Key business rules (where they are enforced)

RuleWhere
Late = in-time after shift start + graceTrigger attendance_before_write. Operator entries use the shift grace; employee self check-in uses at least 15 min (Settings).
GPS check-in inside radius & accuracyFunction self_attendance() — the server measures distance; the phone only sends raw readings.
Absence only by “closing” a dayclose_attendance() — manual button or the 00:30 cron.

7. Entry operator

  • Quick Attendance — choose date & employee, status, press Now for in / out time, late reason if late, Save.
  • Today’s Overview — who is recorded, present, late, not recorded.
  • Entry History — own entries; edit within the allowed window.
  • Correction Requests — ask the admin to fix an older record.
  • Leave Applications — apply on behalf of an employee (admin approves).
  • Daily Expenses — only if the admin enabled it; cannot confirm payment.

8. Employee (phone)

  • First sign-in: username = Employee ID, password 123456 → must choose an own password (8+ characters, letters and numbers).
  • Check In / Check Out — be inside the office, allow location, choose a late reason if asked, press the button. Time comes from the server. Works after an office check-in too.
  • Attendance History, Present Today, My Leave (apply / cancel pending, balances), My Profile (read only).
  • Use a phone: computer location can be ±1500 m and is refused.

Release checklist (staging → production)

  1. All checks pass locally (typecheck, lint, 74 tests, build). Push to staging; Vercel builds the test site automatically.
  2. Apply new migrations to the staging database and test with the staging accounts.
  3. Owner approves in writing.
  4. Back up production: npm run db:backup → backups/<project>-<time>.json (read only, verified after writing; the folder is never committed).
  5. Apply migrations: npm run db:migrate. Each file runs in its own transaction — on any error nothing from that file is kept.
  6. Preservation report: npm run db:backup -- --compare backups/<earlier file>.json → every earlier row must be present and unchanged.
  7. Merge staging into main and push → Vercel deploys the live site in about 2 minutes.
  8. If anything is wrong: Vercel → Deployments → previous production deployment → Instant Rollback. Migrations only add things, so the older code keeps working.
